## Analysis strategy — map everything now, gate later ✅ decided (2026-09-02)
Explicit decision on how "no quality compromise, preserve all the data" translates into pipeline settings vs. downstream analysis choices, so it doesn't get re-litigated per-sample or per-question later:

- **Principle**: abundance/quality "gating" (e.g. "only look at well-expressed genes", "focus on high-confidence calls") belongs entirely in the **downstream DESeq2/edgeR stage in R (Phase 6+)**, applied to a complete count matrix, not as an upstream restriction on what gets aligned/quantified. Reasoning: you don't know what's low- vs. high-abundance until after quantification, so an upstream restriction can only ever guess and discard — irreversibly. A downstream filter on an already-complete matrix can be loosened, tightened, or dropped entirely in seconds, on data you already have.
- **What "gating later" will actually mean in Phase 6**: not a manual abundance cutoff. DESeq2's `results()` runs automatic independent filtering (picks a mean-count threshold from the data itself, to maximize DE genes detected at a given FDR); a light pre-filter (e.g. count ≥ 10 in at least as many samples as the smallest group, n=2 for het/wt) removes near-all-zero noise before fitting, standard DESeq2 practice; edgeR's `filterByExpr()` is the equivalent. This removes noise, not low-but-consistent real signal — the whole point of the kit/depth choice was to be able to detect the latter. Biotype-specific subsetting (e.g. "just the lncRNA hits") is a free post-hoc slice of the same matrix, since every gene carries its Ensembl biotype.
- **Concrete pipeline-side implementation** (`nextflow.config`, added 2026-09-02, validated against the pipeline's own schema — zero warnings):
  - `save_reference = true` — keeps the built STAR/Salmon index in `results/`, so extending this analysis later (e.g. adding more samples) skips a ~30–60 min rebuild and is guaranteed to match these results exactly.
  - `save_unaligned = true` — keeps reads that didn't map to the mouse genome (discarded by default). Real analytical value here, not just a debug artifact: lets you investigate off-target/unannotated/contamination signal later without re-running alignment.
  - `skip_preseq = false` — Preseq is **skipped by default** in nf-core/rnaseq; turned back on here because at 87–144M pairs/sample it directly answers "are we near library-complexity saturation, or would even deeper sequencing still find new unique molecules" — relevant given the whole reason for this depth was to catch low-abundance species.
  - `pseudo_aligner = "salmon"` — runs an independent k-mer-based Salmon quantification alongside the primary `star_salmon` alignment-based one, so low-abundance/non-coding calls have a second, methodologically-different count matrix to cross-validate against later.
  - Deliberately left at default/off: `save_trimmed`, `save_align_intermeds`, `save_umi_intermeds` — regenerable pipeline-internal artifacts (pre-dedup BAMs, intermediate UMI-tools files) with no distinct analytical value over what's already published, and raw FASTQs are already preserved twice (NVMe working copy + untouched `D:` original) — so duplicating them again mid-pipeline buys nothing at real disk cost.
- **Disk impact of these additions**: roughly another 300–500 GB beyond the pipeline's lean defaults (saved index, unaligned reads, second quant track), against 844 GB free on `/` as of 2026-09-02 — comfortable margin, but worth a `df -h` check partway through a run this size rather than assuming.
- **What's explicitly NOT part of this "preserve everything" stance**: adapter/quality trimming, UMI-based PCR-duplicate collapsing, and STAR's standard multimapping filter still run as normal — these remove technical noise (not biological signal) and are standard practice regardless of downstream gating philosophy; see the "Does it preserve your data" discussion this doc pair is meant to capture the outcome of, not re-derive each phase.

3. **Scheduled one-time pause/resume, 2026-09-03** (Asia/Jerusalem time, matches this machine's system clock): pause at **07:30**, resume at **17:00**, via one-time `cron` entries (`crontab -l` on this machine) calling `~/rnaseq-obob/pause_pipeline.sh` and `~/rnaseq-obob/resume_pipeline.sh`. Both scripts log to `~/nf-work/logs/pause_resume.log`. **These are one-time cron entries pinned to 2026-09-03 (day=3, month=9) — remove them (`crontab -e`) after they've fired once, or they'll fire again on the same calendar date next year.**

4. Downstream differential expression: DESeq2/edgeR (R), using the `environment-r.yml` conda env — run inside the same WSL2 Ubuntu, or in RStudio on Windows pointing at the WSL2-generated counts. ## Phase 5b — Disk-full crashes and a Nextflow `-resume` cache-instability bug ✅ diagnosed (2026-09-03 to 2026-09-08)
The original single monolithic `nextflow run ... -resume` approach (all 7 samples in one samplesheet/run) repeatedly failed. Root causes, found by direct evidence (not guessed):

- **Disk genuinely too small at first.** The original WSL2 virtual disk (~1000GB) filled up during the BAM dedup-sort stage (`samtools sort: failed writing ... Illegal seek` — htslib's symptom of `ENOSPC`). Fixed by expanding the WSL2 virtual disk to **1300GB** (`wsl --shutdown` + resize + relaunch) partway through the run.
- **A separate, more serious bug: Nextflow's `-resume` cache became unstable across separate `nextflow` process launches**, even after the disk was fixed. Evidence: the exact same task (identical `.command.sh`, identical resolved input file path) computed a *different* cache hash on every fresh `nextflow` invocation, forcing full re-execution of `UMITOOLS_EXTRACT` → `TRIMGALORE` → `STAR_ALIGN` for already-completed samples, repeatedly, each time wasting hours and hundreds of GB. Traced most likely to WSL2's virtualized disk stack returning inconsistent sub-second file-modification timestamps across separate process launches — Nextflow's default cache mode (`cache = true`) hashes on file path+size+mtime, so a jittery mtime flips the hash every restart even though nothing about the file changed.
  - Contributing/compounding factor: raw FASTQs were briefly symlinked to `D:` (to free local disk mid-run) instead of being real local files; a symlink's own mtime (its creation time) differs from its target's mtime, which independently triggered the same kind of cache miss. Fixed by restoring real local copies at `~/data/raw/` (`cp --preserve=timestamps` from `D:`, so the original Aug-31 source timestamp is preserved) — but this alone did **not** fully stabilize the cache (only partially — some samples still got new hashes on each resume).
  - Partial mitigation applied: `cache = 'lenient'` added to `nextflow.config` (hashes on path+size only, drops mtime) — helped, but did not 100% eliminate the instability within a single monolithic all-7-samples `-resume` run.
- **Net effect of the above**: several redo cycles, ~1TB+ of wasted/orphaned intermediate data generated and cleaned up multiple times, and the one thing genuinely stable throughout every crash/resume was the reference-genome-prep stage (`GUNZIP_FASTA`/`GTF`, `STAR_GENOMEGENERATE`, `SALMON_INDEX`, etc.) — because it depends only on the reference FASTA/GTF, never touched/moved, so its cache hash never drifted. That index (STAR ~27GB + Salmon ~19GB in `nf-work/work`, ~59GB duplicate published copy in `results/genome`) has been deliberately preserved through every cleanup since — rebuilding it from scratch measures at **~1 hour** (`STAR_GENOMEGENERATE` 24m + `SALMON_INDEX` 32m + ~5m of small GTF/fasta prep steps), so keeping it is cheap insurance.

## Phase 5c — New strategy: chunked per-group execution ✅ decided (2026-09-08)
Since the instability bug is specifically triggered by **resuming across separate `nextflow` process launches** (not by a single continuous run), the fix is to stop needing `-resume` at all: run each sample group as its own **one-shot, uninterrupted `nextflow` session**, small enough to finish start-to-finish without a pause.

- **Grouping: `het` (n=2) → `wt` (n=2) → `homo` (n=3)**, run sequentially, each as a separate `nextflow run ... --input <group>_samplesheet.csv` invocation (no `-resume` needed if it completes in one sitting).
- All groups share the same pre-built, already-cached genome/STAR/Salmon index (see Phase 5b) — confirmed to reuse cleanly (`cached: 1 ✔`) since it's untouched by the per-sample instability bug.
- **After each group's run completes**, verify its outputs (counts, BAMs, QC) are correctly present in `results/`, then wipe that group's `nf-work/work/` per-sample intermediates before starting the next group — bounds peak disk usage to roughly one group's alignment footprint (~150-170GB/sample × group size) instead of needing all 7 samples' intermediates simultaneously (which was pushing 900GB-1TB+).
- Cleanup performed 2026-09-08: all per-sample work-dir intermediates and stale partial `results/` output from the crash/redo history removed (~886GB reclaimed), keeping only the genome/STAR/Salmon index. Current state: **~980GB free**, ready to begin the `het` chunk.
- Known-safe fact used for planning: once a sample's `STAR_ALIGN` succeeds, nothing downstream (dedup, BAM-based quant, bigwig, RSeQC/dupRadar/Qualimap QC) ever reads the raw/UMI-extracted/trimmed FASTQ again (verified directly against the pipeline's own subworkflow source, `bam_dedup_stats_samtools_umicollapse/main.nf` — its `take:` block only accepts a BAM+index, no FASTQ channel) — so those FASTQ-stage intermediates (~35-45GB/sample) can be reclaimed mid-group once a sample's alignment is done, if extra headroom is needed within a group.

## Phase 5d — `het` transcriptome-level UMI dedup failures, root cause, and the three-track quantification decision ✅ diagnosed and fixed (2026-09-10 to 2026-09-13)

The `het` chunk's genome-level pathway (STAR→genome BAM→`UMITOOLS_DEDUP`→downstream QC) completed cleanly in ~8.5h/sample, no issues. The **transcriptome-level** pathway (STAR→transcriptome BAM→`UMITOOLS_DEDUP`→`SALMON_QUANT` alignment-mode, which is `star_salmon`'s primary gene-count method) failed repeatedly:

- **First failure**: default 8h time limit, both samples' `UMITOOLS_DEDUP (TRANSCRIPTOME)` hit the cap.
- **Config raised to 48h** based on a *flawed* diagnosis in this doc's earlier revision, which compared het2's *transcriptome*-level secondary-alignment count (2.26B) against het3's *genome*-level count (74M) — an apples-to-oranges mistake (two different BAMs, same generic filename `sample.sorted.bam`). Corrected by direct measurement: true genome-level secondary counts are het2=79.9M vs het3=74.1M (~8% apart, not 30x); true transcriptome-level counts are het2=2.26B vs het3=1.89B (~20% apart). **Both samples have the same underlying problem, not a het2-specific anomaly.**
- **48h also failed for both samples** (het2 at 393M reads parsed, het3 at same deadline) — raising the time limit further would not have fixed this.
- **Actual root cause, found by direct measurement** (`samtools idxstats` on the genome BAM, density = mapped reads / bp): the mitochondrial chromosome (`MT`, 16.3kb) and one unplaced repeat scaffold (`MU069435.1`, likely a collapsed rDNA array) carry **1,300–2,000x normal read density** (231–361 reads/bp for MT vs ~0.15–0.17 reads/bp genome-wide) — classic mt-rRNA/mt-mRNA over-representation from imperfect ribo-depletion in total-RNA kits, present in **both** samples (het3 actually has a higher MT fraction than het2: 2.14% vs 1.22% of mapped reads). `umi_tools dedup`'s directional algorithm scales worse than linearly with pileup depth at a single position, so a few positions dominate total runtime regardless of any time-limit increase.
  - `MU069435.1` was confirmed to have **zero gene annotations** in the GTF, so it never appears in the transcriptome BAM at all — irrelevant to this specific bottleneck (genome-level analysis only, already fine).
  - The 37 mitochondrial transcripts (`ENSMUST00000082387`–`ENSMUST00000084013`, list at `~/nf-work/mt_filtered/mt_transcript_ids.txt`) are the entire cause.
- **Fix applied**: `nextflow.config` now has a targeted override (`withName: '.*BAM_DEDUP_STATS_SAMTOOLS_UMITOOLS_TRANSCRIPTOME:UMITOOLS_DEDUP'`) that fails fast (`time = 2.m`, `errorStrategy = 'ignore'`) instead of retrying for another 48h — this lets every *other* independent output (featureCounts-biotype, RSeQC, StringTie, Qualimap, bigwig, MultiQC, the pseudo-aligner Salmon track) complete normally via `-resume`, which it did (Sep 13, 12:37:57, `Succeeded: 40, Cached: 64, Ignored: 2`).
- A methodologically-correct version of the transcriptome-level Salmon quantification is produced **manually, outside Nextflow** (to avoid the `-resume` cache-hash instability from Phase 5b — do not hand-edit files inside a task's own `work/` cache path): `samtools view -h | awk` filters out the 37 MT transcript IDs from the already-aligned transcriptome BAM (verified by querying a known MT transcript region post-filter, returns 0), then `umi_tools dedup` and `salmon quant --alignments` are run by hand with the exact same arguments nf-core would use (confirmed from the pipeline's own module source, `modules/nf-core/salmon/quant/main.nf` and `conf/modules/quantify_bam_salmon.config`). This is **Track B** below.

### The three quantification tracks (going forward, for all remaining groups)

Two genuinely different questions got conflated during planning and are recorded separately here to avoid repeating that mistake:

- **Track A — fast, unique-count gene expression (nuclear + mitochondrial together).** `featureCounts` (grouped by `gene_id`, standard settings: `-s 2 -p -B -C`) run on the **genome-level** UMI-deduplicated BAM — the pathway that has never had the MT-pileup problem (genome-level dedup only processes primary alignments, so pileup depth at MT doesn't matter). No MT-exclusion hack needed for this track; mitochondrial genes come out correctly deduplicated alongside nuclear ones in the same file. Multi-mapped reads are discarded (not redistributed), so genes with close paralogs/pseudogenes may be undercounted — a real, narrow quality tradeoff, not a broad one. Chosen as the meeting-deadline path for `het` (already have the deduped genome BAMs) and will be run for `wt`/`homo` too once their pipeline runs complete — this still requires the full genome-level pipeline (alignment + ~8.5h/sample dedup) for those new samples, so it is not "instant," just avoids the transcriptome-level bottleneck entirely.
- **Track B — Salmon EM-based cross-validation, nuclear genes only.** The manual, MT-filtered, UMI-deduplicated `salmon quant --alignments` procedure described above. Standard STAR multimapping cap (20, nf-core default) — properly redistributes ambiguous reads across paralogs/isoforms instead of discarding them, which Track A cannot do. **Never produces mitochondrial gene counts** (MT is deliberately excluded from its input) — MT always comes from Track A regardless of whether/when Track B runs. Deferred to a later pass once there's time to let it run to completion (unpredictable duration — see below); will need the same MT-transcript exclusion re-applied for `wt`/`homo` since the same total-RNA kit almost certainly produces the same mt-rRNA over-representation in every sample (not yet verified for `wt`/`homo` specifically — a quick `idxstats` density check on their genome BAMs once available should confirm before assuming the fix transfers cleanly).
- **Track C = Phase 7 below, unchanged.** The permissive-multimapping (`--outFilterMultimapNmax ~100`) TE/L1 retrotransposon track is a **separate biological question** (heterochromatin/TE derepression, not gene-level differential expression), a **separate realignment** (does not reuse any Track A/B BAM), and **separate tools** (TEtranscripts/TElocal, not Salmon). It is not "Track B with a bigger multimapping number" — do not merge these in future planning.

**Honest tradeoff of doing Track A now / Track B later** (for the record, so it isn't re-litigated): this does **not** reduce total project compute — Track B still needs to run for every sample eventually if the cross-validation is wanted, so it's additive work, not a shortcut. What it buys is *time-to-first-usable-result* for a near-term deadline, using the already-proven, non-pathological genome-level pathway instead of waiting on Track B's still-not-fully-characterized transcriptome-level runtime. The specific quality cost is concentrated in genes with paralogs/gene families (undercounted by Track A until Track B is available) — this caveat must be stated whenever Track A results are presented, not left implicit.

Track B manual dedup in progress for both samples (~125M reads parsed each, steady ~3,200-3,700 reads/sec, no reliable total/ETA available — a first attempt at estimating from `idxstats` proved wrong, see reasoning trail in session history). ## Phase 7 — Track C: TE / L1 retrotransposon quantification 📋 planned, not started
This is **Track C** in the Phase 5d three-track framing — a separate biological question from Track A/B's gene-level differential expression, using a separate realignment and separate tools. It is **not** "Track B with a bigger multimapping number"; the permissive `--outFilterMultimapNmax ~100` here has nothing to do with Track B's default-cap (20) Salmon EM quantification. See Phase 5d for why these must stay conceptually separate.

New analytical requirement, added 2026-09-08, **not part of the original Phase 0-6 plan**. Runs only **after** Phase 5 (all three chunks) is fully complete, verified, and its `nf-work/work/` intermediates are wiped — deliberately sequential, not concurrent with Phase 5/Track 1, to avoid holding two independent multi-hundred-GB alignment passes on disk at once (exactly the problem Phase 5b describes).

- **Biological question**: whether obesity drives heterochromatin loss and consequent L1 retrotransposon derepression. Specifically interested in young, full-length, potentially-active L1 subfamilies (`L1Md_A`, `L1Md_T`, `L1Md_Gf`) — not aggregate/whole-LINE signal, which is dominated by degenerate ancient copies and is not informative for this question.
- **Why this needs a separate track, not a config tweak to Phase 5's pipeline**: `star_salmon` (Phase 5) uses standard multimapping handling tuned for gene-level quantification — reads that multimap across near-identical repeat copies (expected and necessary for TE loci) get filtered. nf-core/rnaseq has no TE-aware quantification module. Track 2 requires:
  - A **second, independent STAR realignment** of all 7 samples with permissive multimapping (`--outFilterMultimapNmax ~100`, `--winAnchorMultimapNmax ~200`) — explicitly does **not** reuse Phase 5's BAMs (they already discarded the multimapped reads TE quantification needs).
  - **TEtranscripts** (family-level) **and TElocal** (locus-level) quantification on those realigned BAMs.
  - Normalization for TE counts derived independently — explicitly not reusing Phase 5's DESeq2 size factors.
- **Reusable from Phase 5 (saves real time/disk)**:
  - The **same STAR/Salmon genome index** — multimapping filters are an alignment-time parameter, not baked into the index at build time, so no second index build needed.
  - Likely the same UMI-extracted/trimmed FASTQs — that step is upstream of alignment and doesn't depend on multimapping settings; whether to persist them from Phase 5 or cheaply regenerate (~15-30 min/sample, never the expensive/crash-prone part in this project's history) is a small decision to make when Track 2 starts.
- **New asset needed, not yet obtained**: RepeatMasker-derived TE annotation GTF for mm39/GRCm39 — separate from the Ensembl gene GTF already in `~/data/ref/`. Must record the exact source/version used once obtained.
- **Mandatory QC before trusting any L1 result** (low-input libraries are prone to artifacts that mimic real TE signal): 3′ bias, internal priming, and PCR-duplication skew must be quantified and checked; if a QC metric makes the TE result untrustworthy, that must be reported plainly rather than producing a plot anyway.
- **Disk planning**: needs the same chunked (`het`/`wt`/`homo`, one uninterrupted session per group, clean-up-between-groups) approach as Phase 5c — likely a *larger* per-sample footprint than Phase 5, since permissive-multimapping BAMs (each read potentially reported at up to ~100 locations) are typically bigger than Phase 5's standard-filtered BAMs (which already ran 46-67GB/sample).
- **Caveats flagged when this track was first proposed (2026-09-08), worth re-checking before finalizing the Track 2 plan**: the initial prompt/template describing this track assumed poly-A selection (wrong for this project — the actual kit is ribo-depleted total RNA, which is actually *better* for TE detection since TE transcripts are often poorly polyadenylated) and a 4-group/n=4 design (wrong — actual design is `wt` n=2, `het` n=2, `homo` n=3, per Phase 0). Tissue type was described as "pooled oocytes" in that template but is not confirmed anywhere in this project's own records — verify before it goes into any methods write-up.
